# Transaction and Staging Entry Overview API

## Aggregation Semantics
<!-- AI-UPDATED: 2026-06-26 - DB-derived Missing kept; time-series restored to time_range buckets + zero-fill -->
- Transaction summary endpoints are `GET /overview/transactions` (grouped by rule) and `GET /overview/transactions/rule_account_breakdown` (grouped by rule + configured account); their `time_range` requires `start_time` (with optional `end_time`) and filters by **`transaction.effective_at`** — for `/overview/transactions/rule_account_breakdown` that means the *parent transaction's* timestamp, not the entry's. Since `transaction.effective_at` is the min of its entries', a late entry is still pulled in alongside its transaction; the filter is deliberately transaction-scoped so a transaction's entries move in and out of range as a unit and the range agrees with the `missing` cutoff below (also on `transaction.effective_at`).
- The only time-series endpoint is `GET /overview/transactions/time_series`; `time_range` and `granularity` are required. The other summary endpoints have no time-series variant.
- The DB aggregates per bucket with `date_trunc(granularity, effective_at)` (`hour`/`day`/`week`/`month`) so raw rows are never shipped. Diesel can't `GROUP BY` a computed expression, so the per-bucket aggregation uses window functions partitioned by the bucket + `DISTINCT` (`aggregate_time_series_status_counts_by_rule`). The app separately builds the bucket **axis** (`OverviewTimeBuckets`, capped at `MAX_BUCKETS`) to supply each bucket's `start`/`end` and to zero-fill; the two are complementary, not redundant.
- `Missing` is not stored: a transaction is `expected` until its `effective_at` is older than the rule's aging cutoff (`AgingConfig::missing_before(now())`). The queries return per group the totals **and** the missing subset (`effective_at < cutoff` conditional aggregates — same predicate the paginated list uses, see `transaction_is_missing_expression`); the `Missing`/`Expected` split (`missing` = subset, `expected` = total − subset) is finished in the presentation layer (`ForeignTryFrom<TransactionOverviewRow> for Vec<TransactionStatusAmount>` in `utils::overview`), not the query. Because the cutoff is a per-rule instant tied to the current date, a single bucket can report both `missing` and `expected`.
<!-- AI-UPDATED: 2026-06-29 - bucket helpers moved to overview extension trait with typed errors -->
- **App and DB bucket alignment must match:** `GranularityExt` in `recon::utils::overview` snaps exactly like Postgres `date_trunc` (Monday weeks, 1st-of-month, midnight days, top-of-hour), because the DB row's `date_trunc` start is the lookup key into the `positions` map. Keep these fallible helpers in the overview layer, not on `common_enums::Granularity`, so they can return `OverviewResult`/`OverviewError` directly. A lookup miss is still treated as a bug: `position_for` returns `Option` and the core returns `InternalServerError` rather than misbucketing (which would corrupt counts). The core resolves open-ended `end_time` once and passes the resulting `DefinedTimeRange` to both the axis and the query, so they can't disagree at a boundary.

## Filtering
<!-- AI-UPDATED: 2026-07-14 - rule_ids supported across transaction overview endpoints -->
- All three transaction endpoints (`/overview/transactions`, `/overview/transactions/time_series`, `/overview/transactions/rule_account_breakdown`) accept an optional `rule_ids` query param (`OverviewFilters`/`TimeSeriesFilters` in `api_models::overview`, `OverviewFilters` shared by `/overview/transactions` and `/overview/transactions/rule_account_breakdown`): comma-separated rule IDs, parsed with `parse_comma_separated` the same way `credit_account`/`debit_account` are on `ApiTransactionAccountFilters` (plural name, unlike that struct's singular `rule_id`, since this one accepts a list).
- **Transactions / time-series** (`aggregate_status_counts_by_rule` / `aggregate_time_series_status_counts_by_rule` in `diesel_models::query::transaction`): `rule_ids` is pushed down into the SQL `WHERE` clause as `dsl::rule_id.eq_any(rule_ids)` directly on the `transaction` table, since `transaction.rule_id` is a native column. The rules list is also fetched with `list_recon_rules_by_ids(profile_id, rule_ids)` instead of `list_recon_rules_by_profile_id` when the filter is present — no fetch-all-then-discard — which is what makes the response contain only the requested rules instead of every rule zero-filled. Keep both narrowings in sync if this logic changes.
- **Rule accounts** (`aggregate_status_counts_by_rule_and_account` in `diesel_models::query::transaction`): `entry` has no `rule_id` column — only the parent `transaction` does, keyed by `entry.logical_transaction_id = transaction.transaction_id AND entry.transaction_version = transaction.version`. The query `INNER JOIN`s `transaction` on that composite key and pushes `rule_ids` down as `transaction.rule_id.eq_any(rule_ids)`. The rules list is also narrowed with `list_recon_rules_by_ids` when the filter is present, but the per-rule account set comes from the rule strategy's `get_rule_accounts()`, so **every account configured on a matching rule still appears**, zero-filled if none of its entries match. The `(logical_transaction_id, transaction_version)` join is backed by the composite index of the same name on `entry`, replacing the two single-column indexes; the standalone `transaction_version` index was not useful on its own. Archived versions are excluded from **every** transaction overview aggregate (`transaction.status != Archived` on the summary, time-series, and rule-accounts queries): every edit leaves an archived version behind (~1 per active transaction) and archived analytics are unused. Archived exclusion is enforced in two places: the query drops the real rows, and the shared zero-fill (`zero_filled_transaction_status_breakdown_with_currency`) skips `Archived` so it is not re-added as a phantom `0`. Therefore, `Archived` never appears in any `status_breakdown`.
- No existence check on `rule_ids`: rule IDs from another profile, or that don't exist, are silently dropped, yielding an empty (or partial/zero-filled) response, not a 404 — same "don't leak cross-profile existence" pattern used elsewhere.

## Staging Entry Overview
<!-- AI-UPDATED: 2026-07-14 - GET /overview/staging_entries added -->
- `GET /overview/staging_entries` groups staging-entry statuses by account. Its `time_range` is mandatory (`StagingEntryOverviewFilters.time_range: TimeRange`), so a query without `start_time` gets a 400 instead of an unbounded aggregate.
- Two independent filters, each narrowing a different axis: `account_ids` narrows the **account list itself** (fetched via `list_accounts_by_profile_id_and_account_ids` instead of `list_accounts_by_profile_id` when present — same no-fetch-all-then-discard principle as `rule_ids`), while `transformation_history_ids` only narrows the **aggregation** — every selected account still appears, zero-filled, since an account isn't owned by a single transformation run.
<!-- AI-UPDATED: 2026-08-04 - detailed_status_breakdown added alongside the coarse one -->
- **Two breakdowns per account, from the same rows.** The SQL aggregate groups by the granular `staging_entry.status`, so `detailed_status_breakdown` (`StagingEntryDetailedStatusAmount`, one row per `DieselStagingEntryStatus`) is the direct mapping of the query result, and `status_breakdown` (`StagingEntryStatusAmount`, coarse) is a fold that re-keys those rows on `(ApiStagingEntryStatus::coarse(), currency)` and **sums** them — the ten `needs_manual_review_*` reasons collapse into one `needs_manual_review` bucket. Don't compute the coarse one with a second query. `status_breakdown` dies in step 2 of the status swap (see the transactions `AGENT-NOTES.md` section on the 2-step swap), `detailed_status_breakdown` stays.
- Both zero-fill their whole enum minus `Archived` — 4 rows and 13 rows per account respectively (only `NeedsManualReview` is granular, so the detailed breakdown is the ten reasons plus `Pending`/`Processed`/`Void`) — so an account with no entries still returns a complete breakdown. No `Missing`/aging split, since staging entries don't carry the rule-aging concept transactions do. `Archived` rows are excluded at the query level (`dsl::status.ne(Archived)`, same as `list_v2_paginated`'s default): archived rows are superseded prior *versions* of a staging entry (e.g. the pre-void version, or one consumed into a matched transaction), not distinct entities worth counting — every void produces one, so leaving them in would double-count.
- **`StagingEntryDetailedStatusAmount` flattens its status, `GetStagingEntryResponse` does not.** The breakdown struct has no sibling `status` key, so `#[serde(flatten)]` on the adjacently-tagged `ApiStagingEntryStatus` is safe and its entries serialize as `{"status": …, "sub_status": …, "count": …}` — i.e. the Rust field is `detailed_status` but the wire key is `status`. `GetStagingEntryResponse` can't flatten (its coarse `status` would collide), so there it nests. Both are deliberate; see the transactions `AGENT-NOTES.md`.
- Response includes `account_type` (the account's `BalanceDirection`) alongside `account_id`/`account_name`, as does the transaction rule-account breakdown.

## Response Shape Gotchas
<!-- AI-UPDATED: 2026-07-16 - rule_account_breakdown counts credit/debit separately -->
- `/overview/transactions/rule_account_breakdown` uses `AccountTransactionStatusAmount` (`credit_count`/`debit_count`), not the shared `TransactionStatusAmount` (`count`) used by the other two transaction endpoints. A single account can carry both a credit-direction and a debit-direction entry from the *same* transaction (e.g. a clearing account) — a deduplicated overall count would silently collapse that down to 1. Computed in `aggregate_status_counts_by_rule_and_account` via `count(case_when(balance_direction = ..., id)).aggregate_distinct()`, mirroring the existing `sum(case_when(...))` pattern already used for `credit_amount`/`debit_amount`. Don't widen the shared `TransactionStatusAmount` to add this — the rule-level and time-series responses have no per-account entry split, so a transaction only ever contributes once there.

- Transaction summaries (`/overview/transactions`, `/overview/transactions/rule_account_breakdown`) include every recon rule / configured account and zero-fill the full transaction status enum except `Archived` (which every overview query drops), so empty owners still come back with a complete `status_breakdown`.
- Each transaction time-series bucket carries a `time_range` (`start_time`/`end_time`, clipped to the request) and a `status_breakdown` zero-filled to the full transaction status enum except `Archived`. Every bucket in the range is emitted (including empty ones, fully zeroed), so every bucket has the same shape.
- All responses use `status_breakdown` arrays, not status-keyed objects.
- Amounts are `AmountResponse` values, and aggregation remains grouped by currency, so a status may appear more than once if matching rows span currencies.
